# EatME — Project Plan (V1)

EatME is a Cal AI–style calorie tracker. Users snap a photo of a meal, an AI agent
estimates the calories and macros (protein, carbs, fat), and the app tracks progress
against a personal daily plan that is generated by AI during onboarding.

> V1 definition of done: a simple, **working** app with a clean UI. Payments,
> paywalls, push notifications, weight history, water and exercise tracking are
> explicitly **out of scope** for V1.

---

## 1. Goals

- Personal plan for every user (no generic targets): onboarding answers → AI → daily
  calories, protein, carbs and fat.
- Logging a meal takes one photo. Analysis runs in the background with live progress.
- Production habits from day one: webhooks for user sync, retries for AI jobs,
  error tracking, privacy policy / terms, and account deletion.

## 2. Tech stack

| Concern | Choice |
| --- | --- |
| App framework | React Native + Expo SDK 57, Expo Router (routes in `src/app`) |
| Dev builds | `expo-dev-client` (EAS development build / `npx expo run:ios`), not Expo Go |
| Styling | NativeWind v4 (Tailwind CSS v3) |
| Tabs | Expo Router native tabs (`expo-router/unstable-native-tabs`, liquid glass on iOS 26) |
| Backend | Expo Router API routes (`src/app/api/**/+api.ts`, `web.output: "server"`) |
| Auth | Clerk (`@clerk/expo`) — Google + Apple sign-in only |
| Database | Postgres on Neon, Drizzle ORM (`drizzle-orm/neon-http`) |
| Background jobs / AI agents | Trigger.dev v4 tasks + Realtime hooks (`@trigger.dev/react-hooks`) |
| AI model | OpenAI `gpt-5.6-luna` through OpenRouter (OpenAI SDK with the OpenRouter base URL) |
| Images | ImageKit (storage, optimization, URL transformations) |
| Data fetching | TanStack Query |
| Client state | Zustand (onboarding answers, persisted with AsyncStorage) |
| Errors & monitoring | Sentry (errors, session replay, logs, tracing, user feedback) |
| Legal pages + landing | Static HTML/CSS in `legal/`, deployed to Cloudflare with Wrangler |
| Tests | Manual testing in the simulator / on device (no automated test suites in V1) |

## 3. User flow

```
Welcome ──Get started──▶ Onboarding questions ──▶ Building your plan (AI, live)
                                                        │
                                                        ▼
                         Home ◀── save plan to DB ◀── Sign up (Google / Apple) ◀── Plan ready
```

1. **Welcome** — logo, headline, phone demo image, `Get started`, `Sign in` link.
2. **Onboarding questions** (before auth, answers kept on device):
   1. Gender
   2. Birthday
   3. Height
   4. Current weight
   5. Goal — lose / maintain / gain
   6. Desired weight (skipped when maintaining)
   7. How active are you (weekly)
   8. Weekly pace in kg per week (skipped when maintaining)
   9. Diet — classic / pescatarian / vegetarian / vegan
3. **Building your plan** — answers are sent to `POST /api/plan`, which triggers the
   `generate-plan` Trigger.dev task. The screen follows the run in real time.
4. **Plan ready** — daily calories, protein, carbs, fat + tips. `Continue`.
5. **Sign up** — Clerk Google / Apple. After sign-in the app calls
   `POST /api/onboarding` and the calculated plan is stored in Postgres.
6. **Rule:** a signed-in user without a completed onboarding is always sent to the
   onboarding flow (e.g. someone who taps "Sign in" on the welcome screen with a brand-new
   account). Nobody reaches the home screen without a plan.

## 4. Screens

### Tabs (native tabs): Home · Scan · Profile

**Home**
- Header: logo + streak button (flame + count). Tapping it opens a bottom sheet that
  slides up over a **fading** overlay with a motivational message and the week's
  logged days.
- Horizontal date strip — scrollable back two weeks, never into the future.
- Calories-left card with a ring, three macro cards (protein, carbs, fat) with rings.
- "Today's meals" list (selected day): thumbnail (ImageKit transformation), name,
  time, calories, macros. Meals still analyzing show a live "Analyzing…" card.
  Non-food scans never appear. Tap a meal to edit its values (manual corrections).
- Bottom padding so the tab bar never covers content.

**Scan**
- Ask for camera permission (`expo-camera`), then show the camera with a shutter.
- Gallery button (`expo-image-picker`) to pick a food photo instead.
- Preview with `Retake` / `Analyze the food`.
- Analyze: upload the photo **directly from the app to ImageKit** (signed upload params
  from `GET /api/imagekit/auth`), `POST /api/meals` creates the meal row with the
  `analyzing` status and triggers the `analyze-meal` task, the screen shows an
  optimistic result card that fills in live through Trigger.dev Realtime.
- Not food → "That doesn't look like food" + retake. Transient AI failures are retried
  automatically by Trigger.dev (at least once).
- Result: name, calories, protein, carbs, fat → `Scan another` or `Done`.

**Profile**
- User card, Account section (Personal details — editable, Preferences, Language,
  Upgrade to Family Plan — UI only), Support (Send feedback via Sentry, Privacy
  Policy, Terms of Service), Sign out, Delete account (with confirmation).
- Delete account removes everything: Clerk user, database user, meals, ImageKit images.
- Sentry test bench (development builds only).

## 5. Data model (Drizzle)

**users** — `id` (Clerk user id, PK), `email`, `first_name`, `last_name`, `image_url`,
`gender`, `date_of_birth`, `height_cm`, `weight_kg`, `goal`, `target_weight_kg`,
`activity_level`, `weekly_goal_kg`, `diet`, `unit_system`, `timezone`,
`daily_calories`, `daily_protein_g`, `daily_carbs_g`, `daily_fat_g`, `plan_source`
(`ai` / `formula`), `plan_summary`, `onboarding_completed_at`, `created_at`, `updated_at`.

**meals** — `id` (uuid), `user_id` → users.id (cascade delete), `status`
(`analyzing` / `completed` / `failed`), `name`, `calories`, `protein_g`, `carbs_g`,
`fat_g`, `image_url`, `image_file_id`, `image_path`, `trigger_run_id`, `error`,
`logged_at`, `created_at`, `updated_at`.

The device time zone is stored per user and used for day boundaries and streaks.

## 6. Backend

### Expo API routes
| Route | Auth | Purpose |
| --- | --- | --- |
| `POST /api/webhooks/clerk` | Clerk signature | Verify the webhook, trigger the user-sync task |
| `POST /api/plan` | public | Trigger `generate-plan`, return the run handle for Realtime |
| `GET /api/plan/:runId` | public | Polling fallback for the plan run |
| `POST /api/onboarding` | Clerk | Upsert the user with answers + plan |
| `GET/PATCH/DELETE /api/me` | Clerk | Profile, edits (personal details, time zone), delete account |
| `GET /api/imagekit/auth` | Clerk | Signed params for direct ImageKit uploads |
| `GET/POST /api/meals` | Clerk | List a day's meals / create a meal + trigger analysis |
| `GET/PATCH/DELETE /api/meals/:id` | Clerk | Read, correct or delete a meal |
| `GET /api/streak` | Clerk | Current streak + logged days |

### Trigger.dev tasks (`src/trigger`)
- `clerk-user-created`, `clerk-user-updated`, `clerk-user-deleted` — keep Postgres
  in sync with Clerk (webhook → task, retried automatically).
- `generate-plan` — dietitian prompt → structured daily targets; falls back to the
  Mifflin-St Jeor formula if the AI fails.
- `analyze-meal` — downscaled ImageKit URL → vision model → structured nutrition;
  realtime metadata for progress; `onFailure` marks the meal as failed.

## 7. Error tracking (Sentry)
- `Sentry.init` in the root layout, `Sentry.wrap`, session replay (unmasked in
  development only), structured logs (`Sentry.logger`), tracing with the Expo Router
  navigation integration, user feedback widget.
- Logs: plan generated (info / warn when the formula fallback was used), onboarding
  completed, profile save failed, meal upload failed, meal analysis outcome (camera).

## 8. Legal & landing
- `legal/index.html` landing page, `legal/terms.html`, `legal/privacy.html`,
  `legal/style.css`, phone mockups — same look as the app (white, minimal).
- Deployed to Cloudflare (Wrangler static assets). The app's Privacy / Terms links
  point at the deployed URL (`EXPO_PUBLIC_LEGAL_URL`).
